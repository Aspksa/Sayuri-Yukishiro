# Когнитивное ядро Sayuri — v0.3.0

## Назначение

Когнитивное ядро — это отдельный слой над системным ядром. Оно отвечает не за запуск процесса, а за организацию мышления Sayuri:

- понимание входного запроса;
- определение намерения;
- постановку цели;
- построение плана;
- выбор зарегистрированных способностей;
- проверку риска перед выполнением;
- фиксацию доказательств и квитанций шагов;
- проверку результата;
- оценку уверенности;
- обнаружение противоречий;
- сохранение состояния многошаговой работы;
- восстановление сессии после перезапуска.

Когнитивное ядро не является LLM и может работать без внешней модели. Для будущего подключения модели предусмотрен нейтральный ReasoningProvider.

## Граница безопасности

В v0.3.0 разрешено автоматическое выполнение только способностей уровня READ_ONLY.

Любая способность уровня MUTATION или EXTERNAL блокируется с причиной:

requires_action_broker

Это значит, что когнитивное ядро может решить, что действие нужно, подготовить его и сохранить точку продолжения, но не имеет права самостоятельно изменять внешнее состояние до появления отдельного брокера действий и системы разрешений.

## Когнитивный цикл

Базовый цикл:

1. Получить запрос.
2. Собрать CognitiveContext.
3. Определить Intent.
4. Создать Goal.
5. Построить Plan.
6. Проверить ограничения и противоречия.
7. Оценить уверенность.
8. Выполнить только разрешённые шаги.
9. Для каждого шага записать ExecutionReceipt.
10. Проверить завершённость ResultVerifier.
11. Сохранить состояние и next_action.
12. Завершить checkpoint только после полного завершения плана.

## Намерения

Поддерживаются базовые категории:

- question;
- action;
- analysis;
- creation;
- navigation;
- conversation;
- unknown.

Детерминированный IntentAnalyzer нужен как безопасный фундамент. Позже ReasoningProvider сможет улучшать семантическое понимание без обхода внутренних проверок.

## Цели

Goal хранит:

- уникальный id;
- objective;
- success_criteria;
- constraints.

В каждую цель автоматически добавляются ограничения:

- no_unapproved_mutations;
- preserve_evidence.

## План

Plan состоит из PlanStep. Каждый шаг содержит:

- id;
- title;
- description;
- capability;
- risk;
- depends_on;
- state;
- result;
- error.

Состояния шага:

- pending;
- running;
- completed;
- blocked;
- failed;
- skipped.

## Способности

CapabilityRegistry содержит только явно зарегистрированные способности.

Встроенные способности v0.3.0:

- cognitive.inspect;
- cognitive.synthesize;
- cognitive.compose;
- cognitive.verify;
- cognitive.prepare_action;
- action.execute.

Последняя способность зарезервирована как MUTATION и намеренно не имеет обработчика.

## Доказательства

После каждого вызова шага создаётся ExecutionReceipt:

- receipt id;
- cognitive session id;
- step id;
- capability;
- status;
- evidence;
- created_at.

Квитанции хранятся отдельно от самой сессии, поэтому история выполнения не теряется при обновлении состояния плана.

## Проверка результата

ResultVerifier рассчитывает:

- complete;
- score;
- missing_steps;
- blocked_steps;
- failed_steps.

Когнитивная сессия не может считаться completed, если в плане остался blocked, failed или pending шаг.

## Уверенность и противоречия

CognitiveAssessment использует:

- уверенность классификатора намерения;
- наличие контекстных фактов;
- наличие ограничений;
- наличие плана;
- найденные противоречия.

Это техническая оценка качества состояния, а не утверждение об истинности ответа.

## Провайдер рассуждения

ReasoningProvider — интерфейс для будущего подключения LLM.

Провайдер может:

- дать дополнительную оценку;
- добавить заметки;
- передать метаданные.

Провайдер не получает право напрямую выполнять действия. Его вывод всегда остаётся внутри когнитивного контура и проходит через план, CapabilityRegistry и ExecutionGate.

Если внешний провайдер не подключён, используется NullReasoningProvider.

## Долговечное состояние

SQLite schema v3 добавляет:

- cognitive_sessions;
- cognitive_receipts.

Полное состояние сессии хранит:

- input_text;
- context;
- intent;
- goal;
- plan;
- status;
- confidence;
- contradictions;
- verification;
- provider;
- provider_notes.

## Восстановление

Для каждой незавершённой когнитивной сессии создаётся checkpoint системного ядра:

cognitive:<session_id>

Checkpoint содержит текущее состояние и точный next_action.

При полном завершении сессии checkpoint переводится в completed.

## Локальный HTTP API

Read-only точки:

- GET /api/cognitive
- GET /api/cognitive/sessions

Когнитивное ядро не принимает HTTP-команды на изменение состояния в v0.3.0.

## Что не входит в v0.3.0

- полноценная семантическая LLM;
- память личности и знаний;
- инструменты внешних модулей;
- Action Broker;
- автономные мутации;
- прямой доступ к файлам/почте/вебу;
- самообучение модели.

Эти функции должны подключаться поверх когнитивного ядра через явные интерфейсы.
