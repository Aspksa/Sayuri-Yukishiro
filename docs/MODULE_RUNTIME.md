# Module Runtime Sayuri Yukishiro — v0.4.0

## Назначение

Module Runtime — слой между системным и когнитивным ядром. Он отвечает за то, какие модули существуют, в каком порядке они запускаются, что им разрешено и какие способности они предоставляют когнитивному ядру.

Рантайм не содержит прикладной логики модулей и не выполняет мутации внешнего состояния.

## Расположение модулей

По умолчанию модули ищутся в каталоге `modules/` в корне проекта. Дополнительные каталоги можно указать через `SAYURI_MODULES_DIR` (разделитель — системный `os.pathsep`).

Каждый модуль — отдельный подкаталог, имя которого обязано совпадать с `id` в манифесте:

```text
modules/
  system_probe/
    module.json
    module.py
```

## Манифест module.json

```json
{
  "manifest_version": 1,
  "id": "system_probe",
  "name": "System Probe",
  "version": "0.1.0",
  "description": "Эталонный модуль.",
  "entry_point": "module:SystemProbeModule",
  "enabled": true,
  "requires_core": ">=0.3.0",
  "schema_version": 1,
  "dependencies": [],
  "permissions": ["core.config.read", "core.events.publish", "module.database"],
  "capabilities": [
    {
      "name": "snapshot",
      "risk": "read_only",
      "handler": "snapshot",
      "description": "Read-only наблюдение."
    }
  ]
}
```

Обязательные поля: `id`, `name`, `version`, `entry_point`.

- `id` — строчные латинские буквы, цифры и подчёркивание.
- `version` и `requires_core` — строгий SemVer `MAJOR.MINOR.PATCH`.
- `entry_point` — `<python_файл>:<КлассМодуля>`; файл обязан находиться внутри каталога модуля.
- `schema_version` — ожидаемая версия БД модуля после миграций; при расхождении модуль не запускается.
- `enabled: false` — модуль обнаружен, но осознанно не запускается.

Любое нарушение формата — это отказ с явной причиной, а не тихое игнорирование.

## Требования к версиям

Поддерживаются три спецификатора:

| Запись | Значение |
|---|---|
| `>=1.2.0` | версия не ниже указанной |
| `==1.2.0` | строго эта версия |
| `~>1.2.0` | совместимая по MINOR: `>=1.2.0` и `<1.3.0` |

Запись без оператора (`1.2.0`) трактуется как `>=1.2.0`.

## Обнаружение

Ошибка одного манифеста не отменяет обнаружение остальных. Причины отказа фиксируются в `discovery.rejected`:

- отсутствует `module.json`;
- манифест не является корректным JSON;
- нарушен формат полей;
- `id` не совпадает с именем каталога;
- дубликат `id` (побеждает первый найденный каталог).

## Граф зависимостей

`DependencyResolver` строит детерминированный порядок запуска (топологическая сортировка с сортировкой по `id` внутри уровня) и отклоняет модули с причинами:

| Причина | Когда |
|---|---|
| `incompatible_core` | `requires_core` не удовлетворён версией системного ядра |
| `missing_dependency` | зависимость не установлена |
| `dependency_disabled` | зависимость отключена в манифесте |
| `incompatible_dependency` | версия зависимости не удовлетворяет требованию |
| `dependency_unresolved` | каскад: зависимость сама отклонена |
| `dependency_cycle` | модуль участвует в цикле зависимостей |

## Разрешения

Выдаются автоматически (чтение и собственная БД модуля):

- `core.config.read`
- `core.events.publish`
- `core.jobs.submit`
- `core.checkpoints.write`
- `module.database`

Остаются заблокированными до появления Action Broker:

- `system.process`
- `network.outbound`
- `filesystem.write`

Модуль, запросивший заблокированное разрешение, переходит в состояние `blocked` и не запускается: платформа не выдаёт частичные права молча. Внутри модуля доступ идёт через `ModuleContext`, который проверяет разрешение на каждом вызове.

## Миграции модульных БД

Модуль владеет только своей БД `data/modules/<id>.db` и объявляет миграции в коде:

```python
def migrations(self):
    return (Migration(version=1, description="notes", statements=("CREATE TABLE ...",)),)
```

Правила:

- номера строго возрастают начиная с 1 и не переиспользуются;
- каждая миграция применяется один раз и в одной транзакции;
- применённые версии хранятся в таблице `module_migrations` самой БД модуля;
- если в БД есть версия, не объявленная кодом, запуск отклоняется: БД новее модуля;
- после миграций фактическая версия сверяется с `schema_version` манифеста.

## Жизненный цикл

```text
discovery -> permissions -> load (entry_point) -> migrate -> on_start
          -> регистрация способностей -> health -> on_stop
```

Состояния модуля: `discovered`, `disabled`, `rejected`, `blocked`, `loaded`, `migrated`, `running`, `stopped`, `failed`.

Остановка идёт в обратном порядке запуска. Состояния сохраняются в таблице `module_states` центральной БД (схема SQLite v4).

### Поведение при сбое

По умолчанию (`modules.strict_startup: false`) сбой изолируется:

- упавший модуль получает состояние `failed`;
- его `on_stop` вызывается, способности снимаются, Python-модуль выгружается;
- зависимые модули получают `blocked` с причиной `dependency_failed`;
- остальные модули продолжают запуск;
- создаётся checkpoint системного ядра с точным `next_action` для восстановления.

В строгом режиме (`modules.strict_startup: true`, либо `SAYURI_MODULES_STRICT_STARTUP=1`) выполняется полный откат: все уже запущенные модули останавливаются, рантайм не считается запущенным, ошибка поднимается наверх.

## Способности модулей и когнитивное ядро

Способности запущенного модуля регистрируются в когнитивном `CapabilityRegistry` под именем `module.<module_id>.<name>` и снимаются при остановке модуля.

Граница безопасности сохраняется: автоматически исполняются только способности уровня `read_only`. Способности уровня `mutation` и `external` регистрируются без обработчика, и `ExecutionGate` отклоняет их с причиной `requires_action_broker`. Отдельная причина `module_permission_denied` отклоняет способность модуля, которому не выданы разрешения.

## Health и API

`ModuleRuntime.health()` агрегирует состояния: `healthy`, `degraded` (есть заблокированные, отклонённые или нездоровые модули), `failed` (есть упавший модуль). Исключение внутри `health()` модуля не ломает рантайм — модуль считается нездоровым.

Локальный read-only API:

| Эндпоинт | Содержимое |
|---|---|
| `/api/modules` | реестр модулей центральной БД |
| `/api/modules/runtime` | полное состояние рантайма: каталоги, discovery, граф, модули, health |
| `/api/modules/health` | только агрегированное состояние модулей |
| `/api/modules/states` | сохранённые состояния модулей из БД |

Диагностика `--preflight` содержит проверку `module_runtime`.

## Границы слоя

1. Модуль не обращается к системному ядру напрямую — только через `CoreAPI` внутри `ModuleContext`.
2. Модуль не трогает БД других модулей.
3. Модуль не управляет своим запуском и остановкой.
4. Модуль не получает права на мутацию внешнего состояния до Action Broker.
